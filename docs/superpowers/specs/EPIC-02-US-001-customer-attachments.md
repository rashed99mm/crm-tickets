# Customer attachments

**Date:** 2026-08-26
**Story:** `MVP-06` in [`../../requirements/mvp/epic-2-customer-records.md`](../../requirements/mvp/epic-2-customer-records.md)
**Brief area:** 1 — Customer Management ("notes and attachments")
**Depends on:** `MVP-04`'s customer detail screen — attachments have nowhere to live without it.

## Problem

Customers send screenshots, invoices and logs. Today those live in an agent's inbox, so the next
person to pick up the account cannot see the evidence the last conversation turned on.

## Why this spec adds only frontend criteria

`AC-22`…`AC-28` are **already approved** and cover upload, the size cap, the content-type allowlist,
the traversal defence, download and delete. The schema is built: `Assets` is the single file
catalogue and `CustomerAttachments` is a thin ownership link, both shipped in Phase 0 with
`AC25_The_Stored_Name_Is_Server_Generated_And_Cannot_Escape_The_Directory` passing at entity level.

What has never been specified is the **screen**. This appends `AC-83`…`AC-85`.

## Assumptions

- **A18.** Files live on the local filesystem behind an `IFileStore` port, in a directory **outside**
  the web root. Object storage is a later concern and the port exists so it can be swapped without
  touching a handler.
- **A19.** Attachments belong to a customer, not a ticket — brief area 1 places them under Customer
  Management. A future `TicketAttachments` link table reuses the `Assets` catalogue.
- **A20.** Limits: **10 MB**, and an allowlist of `image/png`, `image/jpeg`, `image/gif`,
  `application/pdf`, `text/plain`. An allowlist because a blocklist is a list of the attacks someone
  already thought of.

## Out of scope

Virus scanning · thumbnails or previews · versioning · drag-and-drop reordering · attaching to a
ticket · public links.

## Acceptance criteria

Existing and approved: `AC-22` (upload returns stored metadata), `AC-23` (over the size limit → 413,
**nothing written to disk**), `AC-24` (type outside the allowlist → 415, nothing written), `AC-25`
(a hostile filename cannot escape the directory; the stored name is server-generated), `AC-26`
(download requires authentication and carries the right content type and filename), `AC-27` (unknown
customer → 404), `AC-28` (delete removes the row and the file).

Appended here:

- **AC-83** (P1) Given a customer's detail screen, then their attachments are listed with original
  filename, size and type, beside the notes.
- **AC-84** (P1) Given I choose a file, then it uploads and appears in the list without a page
  reload. A file the **client** can already tell is too large or of the wrong type is refused before
  a request is sent — and the server refuses it independently regardless.
- **AC-85** (P1) Given an attachment, then I can download it, and remove it after a confirmation.

## Design

### API

| Endpoint | Notes |
|---|---|
| `GET /api/Customers/{id}/attachments` | paged; id, original filename, content type, size, uploader, when |
| `POST /api/Customers/{id}/attachments` | `multipart/form-data`, one file |
| `GET /api/Customers/{id}/attachments/{attachmentId}/content` | streams; `Content-Disposition` |
| `DELETE /api/Customers/{id}/attachments/{attachmentId}` | soft-deletes the link, retires the asset, removes the file |

### The three defences, and the order they run in

The order is the design. Each must refuse **before** the next cost is incurred:

1. **Size** — checked against `Content-Length` and enforced by the request-body limit, so an
   oversized upload is rejected **before the stream is consumed**. `AC-23` says "nothing is written
   to disk"; a check after buffering has already failed that.
2. **Content type** — allowlist, checked before any write.
3. **Path** — the stored name is `Guid + extension`, generated by `Asset.Create`. The original name
   never reaches the filesystem. The resolved path is asserted to sit under the configured root
   before any write, because a defence that depends only on name generation being correct is one
   bug from a traversal.

### `IFileStore`

```csharp
public interface IFileStore
{
    Task SaveAsync(string storedFileName, Stream content, CancellationToken ct);
    Task<Stream?> OpenAsync(string storedFileName, CancellationToken ct);
    Task DeleteAsync(string storedFileName, CancellationToken ct);
}
```

Declared in `Application`, implemented in `Infrastructure` over the local filesystem, rooted at a
configured path. The implementation resolves and asserts containment on every call.

## Testing

`AC-23`, `AC-24` and `AC-25` each need a test that asserts **the filesystem is untouched**, not
merely that the status code was right. A handler that writes then deletes passes a status-only
assertion and fails the criterion.

`AC-25`'s test uploads `../../etc/passwd` and `..\..\windows\system32\config\sam` and asserts the
storage root contains exactly one new file, named as a GUID.
